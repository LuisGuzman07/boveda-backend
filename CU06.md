# CU-06 — Crear nueva bóveda cifrada

El módulo añade tres tablas mediante la revisión `c00620260917`. No cambia las tablas ni los servicios de CU-01 a CU-05. La API recibe únicamente sobres AES-256-GCM, parámetros Argon2id y UUID. El propietario se obtiene de la sesión, nunca del cuerpo.

## Preparación

Desde `boveda-backend`, con PostgreSQL encendido:

```powershell
docker compose run --rm --no-deps backend alembic upgrade head
docker compose run --rm --no-deps backend pytest -q tests/test_vault.py
```

La suite CU-06 usa SQLite en memoria y no modifica la base local. Reinicia el backend después de actualizar el código. El cliente requiere un usuario con `vaults:create`, MFA TOTP activo y un dispositivo autorizado.

Para validar también en PostgreSQL, usa únicamente una instancia local y descartable
con un nombre `boveda_lote2b_tmp*`, `boveda_lote2b_temp*` o `boveda_lote2b_test*`.
La suite reinicia el esquema `public` antes y después de cada prueba, por lo que no
debe apuntar a la base de Docker Compose ni a una base persistente:

```powershell
$env:CU06_TEST_POSTGRES = "1"
$env:BOVEDA_L2B_DISPOSABLE_DATABASE = "1"
$env:DATABASE_URL = "postgresql+psycopg://boveda_test@127.0.0.1:55432/boveda_lote2b_test_ci"
python -m pytest -q tests/test_vault.py
```

## Contrato

- `POST /api/v1/vaults/session`: access token existente más refresh token, TOTP y clave pública Ed25519 registrada. Entrega una sesión exclusiva de bóvedas de 15 minutos, ligada a la fila `sesion`, usuario y dispositivo.
- `POST /api/v1/vaults`: requiere `Idempotency-Key`; crea bóveda, membresía del propietario, sobre y auditoría en una transacción.
- `GET /api/v1/vaults`: devuelve bóvedas con un sobre activo dirigido al dispositivo autenticado.
- `GET /api/v1/vaults/{uuid}`: recupera metadatos cifrados y sobre autorizado; un administrador no tiene acceso automático a claves ajenas.

Las operaciones de bóveda verifican en cada solicitud usuario activo, sesión vigente/no revocada, dispositivo activo/confiable, clave pública y firma Ed25519. El mensaje firmado es `jti\ntimestamp\nMETHOD\n/api/v1/vaults...\nIdempotency-Key\nsha256(body)`, en UTF-8. El cuerpo es el JSON exacto transmitido. El timestamp tiene una tolerancia de 60 segundos. GET no admite filtros/query strings. La clave de idempotencia es única por propietario: repetir el mismo contenido devuelve la misma bóveda, cambiar el contenido devuelve 409. El UUID de bóveda se genera en el cliente para asociar los sobres mediante AAD.

## Formato criptográfico v1

Cada sobre contiene `algoritmo=AES-256-GCM`, `ciphertext`, `nonce` de 12 bytes y `tag` de 16 bytes, codificados Base64. La sal Argon2id tiene 16 bytes. Parámetros fijos: 65536 KiB, 3 iteraciones, paralelismo 1, salida de 32 bytes.

Flutter genera una clave aleatoria de bóveda de 32 bytes. Primero la cifra con la clave derivada de la contraseña maestra y luego cifra el JSON de ese sobre con una clave local de dispositivo de 32 bytes. La clave local se almacena con `flutter_secure_storage`, separada por usuario, no en SharedPreferences. La clave Ed25519 también se conserva en almacenamiento seguro. Las claves se destruyen/limpian en lo posible; Dart no garantiza el borrado de todas las copias de memoria.

AAD exacta: `${id_boveda}:password:v1` para la primera envoltura; `${id_boveda}:${id_dispositivo}:device:v1` para la segunda; `${id_boveda}:name:v1` y `${id_boveda}:description:v1` para metadatos. El backend guarda solo el sobre exterior. Cambiar contraseña de cuenta no afecta esta envoltura. El bloqueo local no altera el estado global ACTIVA de la bóveda.

El módulo no implementa compartir, rotación, Emergency Kit, archivos, MinIO ni S3. La reapertura verifica el sobre y los metadatos; CU-07 deberá integrar biometría y el ciclo de vida de la clave desbloqueada. CU-08 debe generar una clave y nonce independientes por versión de archivo, no reutilizar el nonce ni directamente la clave de metadatos. Perder las claves locales del dispositivo puede hacer inaccesible la bóveda; no existe recuperación automática por contraseña de cuenta.

## Coordinación con CU-07

La pantalla de creación solicita siempre la contraseña maestra. No conserva la clave derivada ni la contraseña. CU-07 puede incorporar un sobre local adicional protegido por biometría para desbloquear sin repetir esa contraseña, conservando el formato servidor v1. El uso de almacenamiento seguro por sí solo no demuestra hardware no exportable ni exige biometría; esas garantías deben implementarse y probarse en CU-07.
